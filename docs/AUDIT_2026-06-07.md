### `agent-framework` floor bump rationale

AF 1.8.0 (released 2026-06-04) delivers two fixes that are directly material to Gantry production use:

1. **Message-id collision fix in compaction** — benefits `GantryContextProvider`. Previous versions could produce duplicate message IDs during context compaction, leading to silent message drops in long multi-turn sessions.
2. **Unsafe serialisation fix in AF observability layer** — benefits `GantryToolBridge`. Previous versions could silently corrupt structured function arguments when AF's built-in telemetry serialised them.

Both are production-critical bugs in multi-agent workflows. Requiring 1.8.0 as the minimum ensures all users pick up both fixes automatically. The breaking change in 1.8.0 (`github-copilot-sdk` upgrade to v1.0.0) does not affect Gantry.

Source: https://github.com/microsoft/agent-framework/releases

### `anthropic` floor bump rationale

Versions 0.106.0 (2026-06-05) and 0.107.0 (2026-06-06) are patch/minor releases with no breaking changes to the Messages API, tool-use, or streaming surfaces used by Gantry. Bumping the floor to 0.107.0 keeps the documented floor aligned with the latest tested version and avoids users installing stale SDK releases that predate minor improvements.

Source: https://pypi.org/pypi/anthropic/json

## Phase 3 — Provider API Refactors

### OpenAI

**Assessment: No changes required.**

The existing `OpenAIAdapter` (Chat Completions) and `OpenAIResponsesAdapter` (Responses API) correctly implement:
- Chat Completions: `{"type": "function", "function": {"name": ..., "description": ..., "parameters": ...}}`
- Responses API: `{"type": "function", "name": ..., "description": ..., "parameters": ...}`
- Tool result round-trip: `{"type": "function_call_output", "call_id": ..., "output": ...}`

The `openai_demo.py` uses `gpt-4.1` for Responses API calls and `gpt-5.5` for Chat Completions, both of which are current (the `gpt-4o` / `gpt-4o-mini` sunset on 2026-10-23 was pre-emptively handled in the previous audit cycle).

Source: https://platform.openai.com/docs/api-reference/responses

### Anthropic

**Assessment: No changes required to adapters. Model IDs are current.**

The `AnthropicAdapter.to_provider_schema()` correctly generates:
```json
{
  "name": "...",
  "description": "...",
  "input_schema": { ... }
}
```
with optional `"strict": true` + `"additionalProperties": false` injection for strict mode. This matches the current Messages API tool definition format.

Source: https://platform.claude.com/docs/en/docs/build-with-claude/tool-use/overview

The `anthropic_demo.py` uses `claude-sonnet-4-6`, which is the current recommended Sonnet model per https://platform.claude.com/docs/en/about-claude/models/overview.

**Note:** `claude-sonnet-4` and `claude-opus-4` were deprecated and retire 2026-06-15. These model IDs do not appear anywhere in Gantry's codebase or examples — no action required.

### Google Gemini

**Finding: `GeminiAdapter.format_tool_result` docstring updated to document Gemini 3's mandatory `id` field.**

The implementation itself is correct — the `id` is conditionally placed inside `functionResponse`. The Gemini 3 API mandates this field for parallel function call correlation; callers must pass `tool_call_id` sourced from `FunctionCall.id`. The docstring previously did not make this requirement explicit.

Source: https://ai.google.dev/gemini-api/docs/function-calling

Diff applied to `agent_gantry/adapters/tool_spec/providers.py`:
```diff
-    def format_tool_result(self, tool_name, result, tool_call_id=None, *, is_error=False):
-        """Format result for Gemini function response."""
+    def format_tool_result(self, tool_name, result, tool_call_id=None, *, is_error=False):
+        """Format result for Gemini function response.
+
+        .. important::
+            Gemini 3 models **mandate** a unique ``id`` in every function
+            response. Always pass ``tool_call_id`` (sourced from
+            ``FunctionCall.id``) when targeting Gemini 3 models.
+            Source: https://ai.google.dev/gemini-api/docs/function-calling
+        """
```

The `google_genai_demo.py` correctly uses `types.Part.from_function_response()` with `id` from `fn.id`. No example changes needed.

## Phase 5 — Universal Tool-Calling Design

### Current contract

```
ToolDefinition (canonical internal)
    → ToolSpecAdapter.to_provider_schema()     → provider-specific schema dict
    ← ToolSpecAdapter.from_provider_payload()  ← provider tool-call response
    → ToolSpecAdapter.format_tool_result()     → provider result message
    → ToolCallPayload (unified intermediate)
    → ToolCall (for gantry.execute())
```

All paths are covered by `agent_gantry/adapters/tool_spec/providers.py`.

### Provider schema shapes (verified)

| Provider | Tool schema | Tool call ID field | Result format |
|----------|-------------|-------------------|---------------|
| OpenAI Chat Completions | `{"type": "function", "function": {"name": ..., "description": ..., "parameters": ...}}` | `id` on tool call | `{"role": "tool", "content": ..., "tool_call_id": ...}` |
| OpenAI Responses API | `{"type": "function", "name": ..., "description": ..., "parameters": ...}` | `call_id` | `{"type": "function_call_output", "call_id": ..., "output": ...}` |
| Anthropic | `{"name": ..., "description": ..., "input_schema": ...}` | `id` on `tool_use` block | `{"type": "tool_result", "tool_use_id": ..., "content": ...}` |
| Gemini | `{"name": ..., "description": ..., "parameters": ...}` | `id` on `FunctionCall` (Gemini 3) | `{"functionResponse": {"name": ..., "response": ..., "id": ...}}` |
| Mistral / Groq | Inherits `OpenAIAdapter` (OpenAI-compatible) | `id` | OpenAI `tool` role message |
| Agent Framework | Inherits `OpenAIAdapter` + optional metadata | — | Python callable (no serialised result) |

All shapes verified against current provider documentation.

### Identified type annotation bug

`GantryToolBridge.build_agent` and `as_agent` had `score_threshold: float | None` despite the class-level attribute and `get_tools` accepting `float | str | None`. This created a false narrowing that prevented IDEs from accepting `"relative:0.8"` style thresholds.

**Fixed.** Both methods now annotate `score_threshold: float | str | None`.
